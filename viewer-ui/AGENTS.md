# viewer-ui scope

Follow the [root AGENTS.md](../AGENTS.md) for repository-wide workflows. This guide covers boundaries that are easy to miss only in this directory, such as the contract between the viewer and server, the bundle, and the development server.

## Frontend contracts

- HTTP, SSE, and WebSocket types, encoders, and decoders in `viewer-ui/src/api.ts` and `viewer-ui/src/api/` are the counterpart to `src/web/viewer/dto/` and the server terminal protocol. If fields, enum variants, message order, or paths change, update both implementations and their contract or integration tests together.
- `api.fixture.json` is a committed wire fixture generated from Rust DTOs. If a Rust payload changes, regenerate it from the repository root with `UPDATE_API_FIXTURE=1 cargo test the_wire_fixture`, review the fixture diff, then align the TypeScript API types. Do not edit the fixture by hand to hide contract drift.
- Verify API contract changes with the frontend gate in the [shared verification procedure](../docs/getting-started.md#building-and-testing). Type assignments in `api.contract.test.ts` catch missing, renamed, or retyped fields; the Rust fixture test pins payloads added or removed by the server.

## Bundle and development server

- `viewer-ui/dist/` is the committed release bundle generated by Vite and embedded in the Rust server binary. After changing source, configuration, or public assets that affect the bundle, build it and include the matching `dist` output in the final changes. On a clean checkout, rerunning the same build must leave no uncommitted changes in `dist`.
- The relative asset base and `/api`, `/login`, and `/ws` development proxies in `vite.config.ts` are part of the deployment contract between the embedded server and Vite development server. When changing a mount path or server port, check the Rust routes, documentation, and verification as well.
- Put page composition in `pages/`, reusable UI in feature directories under `components/`, and state and effects in responsibility-based directories under `hooks/`. Handle server wire contracts at the `api/` boundary. Put behavior and calculation helpers shared by multiple pages or hooks in responsibility-based directories under `lib/`. `lib/` may include React hook dependencies, so do not treat it as a pure-function-only layer. Do not reinterpret server wire strings in hooks; pass validated types from `api/` instead.
- Keep tests and harnesses with the feature they cover, and reserve `lib/shared/` for helpers used by multiple features. Preserve dynamic-import lazy-loading boundaries when moving files.
